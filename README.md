**Companion repository:** [36120-at2-experiments](https://github.com/vigneshcrack/36120-at2-experiments) (model training/experimentation)

A FastAPI service that serves two machine learning models trained on Sydney, NSW historical
weather data from the [Open-Meteo Historical Weather API](https://open-meteo.com/):

- **Climate Comfort Index (CCI)** - a 0-100 regression score describing how pleasant outdoor
  conditions are expected to be, forecast 1, 2 and 3 days ahead.
- **Weather Hazard Category (WHC)** - a 4-class risk label (Low / Moderate / High / Extreme
  Risk), forecast exactly 7 days ahead.

Both models are sklearn `Pipeline` objects (preprocessing + trained estimator bundled together)
produced by the experimentation repository above; see that repository's notebooks for the full
model development, evaluation, and justification.

## How prediction works

Both prediction endpoints take a single `date` query parameter - nothing else. Internally, the
API fetches the preceding ~2 weeks of historical weather for Sydney from the Open-Meteo Historical
Weather API (via the custom `mykrml_25740287` package, the same package used in the
experimentation repository), reconstructs the exact same engineered features used at training
time (cyclical month encoding, 7-day and 3-day rolling statistics), and calls the appropriate
trained model's `.predict()`. This means predictions require live internet access to Open-Meteo's
archive at request time, and are only available for dates within Open-Meteo's historical coverage
(dates too recent to have settled archive data, or before Open-Meteo's records begin, will return
a `422`/`503` error rather than a fabricated prediction - see **Error handling** below).

## Endpoints

| Method | Endpoint | Description |
|---|---|---|
| GET | `/` | Project overview and self-documentation |
| GET | `/health` | Health check |
| GET | `/predict/index/comfort_climate?date=YYYY-MM-DD` | Predict CCI for date+1, date+2, date+3 |
| GET | `/predict/category/weather_hazard?date=YYYY-MM-DD` | Predict WHC for exactly date+7 |
| GET | `/model-metadata` | Metadata (algorithm, features, feature importance, performance) for both models |

Interactive API docs (Swagger UI) are auto-generated by FastAPI at `/docs` once the service is
running.

### Why the CCI endpoint returns 3 models' worth of predictions, not 1

The experimentation repository's CCI notebook trains and rigorously evaluates a single
3-day-ahead model (with full leakage-prevention, citation-backed justification, and systematic
hyperparameter tuning - see that repository for the complete analysis). To satisfy this API's
requirement of returning day+1, day+2, *and* day+3 predictions from one request, two additional
lightweight models (1-day-ahead and 2-day-ahead) were trained using the exact same feature
pipeline and the same tuned hyperparameters as the graded 3-day-ahead model. These two supporting
models are deployment infrastructure only - the 3-day-ahead model remains the one analysed in
depth in the experimentation repository and final report.

## Error handling

The API validates input and fails gracefully rather than crashing or returning a raw stack trace:

| Situation | Status code | Example response |
|---|---|---|
| Missing `date` parameter | `422` | `{"detail": [...]}` (FastAPI's standard validation error) |
| Malformed `date` (wrong format, invalid calendar date) | `422` | `{"detail": "Invalid 'date' value: '2024/06/15'. Expected an ISO-8601 date in YYYY-MM-DD format, e.g. '2025-01-01'."}` |
| Date outside Open-Meteo's historical coverage / not enough trailing history | `422` | `{"detail": "No weather observations are available for 1900-01-01. ..."}` |
| Open-Meteo temporarily unreachable | `503` | `{"detail": "Unable to retrieve historical weather data needed to build a prediction for ... The upstream weather data source may be temporarily unavailable. ..."}` |
| Missing model artefact files at startup | fails fast at container startup with a clear `RuntimeError`, rather than failing per-request | - |

## Local setup and development

This project uses [uv](https://docs.astral.sh/uv/) for environment and dependency management,
consistent with the rest of this assignment.

1. Clone this repository and `cd` into it.
2. Install dependencies (this also installs the custom `mykrml_25740287` package from TestPyPI):
   ```bash
   uv sync --extra-index-url https://test.pypi.org/simple/ --index-strategy unsafe-best-match
   ```
3. Run the app locally in dev mode:
   ```bash
   uv run fastapi dev app/main.py
   ```
4. Check it's working:
   - `http://127.0.0.1:8000/` - project overview
   - `http://127.0.0.1:8000/health` - health check
   - `http://127.0.0.1:8000/docs` - interactive Swagger UI, useful for manually trying the
     prediction endpoints with different dates
   - `http://127.0.0.1:8000/predict/index/comfort_climate?date=2024-06-15`
   - `http://127.0.0.1:8000/predict/category/weather_hazard?date=2024-06-15`

## Running the tests

```bash
uv run pytest tests/ -v
```

The prediction-endpoint tests mock the live Open-Meteo call (patching
`fetch_historical_weather`/`aggregate_daily_weather` in `app.main`) with a real historical data
sample bundled under `data/`, so the full test suite runs offline and deterministically - no
network access or API keys required. Tests cover both the happy path for every endpoint and
robustness/error-handling requirements: missing parameters, malformed dates, dates outside
historical coverage, and upstream fetch failures.

## Deployment (Render)

1. Push this repository to GitHub (private repo, per the assignment brief).
2. In the [Render Dashboard](https://dashboard.render.com/): **New → Web Service**, connect this
   GitHub repository.
3. Configure the service:
   - **Language:** Docker (Render will use the `Dockerfile` in this repo directly)
   - **Instance Type:** Free tier works for demonstration, but note Render's free tier spins
     down after a period of inactivity - the first request after idling will be slow (cold
     start) while the container restarts. If the service needs to be reliably instantly
     responsive at marking time, consider pinging the `/health` endpoint shortly before marking,
     or upgrading to a paid always-on instance for the marking window.
   - **Environment Variables:** none required - the Dockerfile's `CMD` already reads Render's
     `$PORT` automatically.
4. Click **Deploy Web Service** and allow a few minutes for the first build.
5. Once deployed, verify the live URL responds correctly at `/`, `/health`, and both prediction
   endpoints before submitting.

## Troubleshooting

- **`RuntimeError: Could not load model artefacts...` at startup** - the `models/` directory
  must sit directly alongside `app/` (not inside it). Confirm all four `.joblib` files are present
  and were not accidentally excluded by `.gitignore` or `.dockerignore`.
- **A prediction request returns `503`** - this means Open-Meteo's API could not be reached at
  request time (network issue on the server, or Open-Meteo itself is briefly down). Retry after a
  short wait; this is not a bug in the model.
- **A prediction request returns `422` for a date that "should" work** - check the date is not
  too close to Open-Meteo's present-day boundary (very recent dates may not have settled archive
  data yet) and not before Open-Meteo's historical coverage begins.
- **`uv sync` fails to find `mykrml-25740287`** - make sure the `--extra-index-url` and
  `--index-strategy unsafe-best-match` flags are included exactly as shown above; the package is
  published to TestPyPI, not the main PyPI index.
